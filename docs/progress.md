## Database model and boundaries

- Projects and tasks are scoped to the verified caller's selected workspace membership. Membership identity uses provider issuer/subject; email is optional and informational. The API has workspace listing, owner-only member creation, and per-request workspace authorization.
- Tasks reference projects with deletion restricted. Workspace-scoped task deletes and empty-project deletes are implemented and audited; projects with tasks return 409. Document metadata references a workspace and optionally a project; its GET endpoint is workspace-scoped, and project deletion detaches rather than deletes metadata. There is no file-byte storage/download endpoint.
- The project/task API contract remains stable. The frontend still reads `web/src/features/projects/data.ts` and local feature state; a later integration phase will put a typed HTTP client behind the existing data boundary.
- Index rationale: `(workspace_id, name/customer)` supports the project list’s common workspace sort paths; `(project_id, due)` supports per-project due-date listing and project FK lookups; `(status, due)` supports filtered due-date listing; document indexes support workspace/project lookup; `(workspace_id, created_at)` supports ordered audit inspection. Live planner choice still needs measurement.
