# OpsDesk Phase 04 threat model

Scope: Auth0 browser sign-in, FastAPI bearer-token validation, PostgreSQL workspace memberships, and current project/task plus document-metadata APIs. Project/task records in the web UI remain demo data. File bytes, deployment hardening, and full frontend CRUD integration are outside this phase.

| Threat and asset | Realistic attack path | Current mitigation | Evidence | Remaining risks / assumptions |
| --- | --- | --- | --- | --- |
| Account takeover or stolen credentials; workspace records | Attacker steals an account password or active session. | Auth0 owns password, reset, MFA, and account recovery. The browser uses authorization code + PKCE and in-memory token caching; the API requires a signed access token. | User-confirmed manual browser checks: Auth0 sign-in reached the workspace dashboard and sign-out worked. The owner workspace API request succeeded; a second user without membership was denied by both workspace UI access and API. Provider-independent signed-token tests also passed. | Expired/revoked-token UI handling is not manually verified. Auth0 MFA policy, TLS, device security, and incident response require tenant/deployment review. Logout clears the browser session but does not revoke a copied self-contained JWT before expiry. |
| Insecure direct object reference; projects/tasks/doc metadata | Caller changes a resource UUID to one belonging to another workspace. | Every request resolves `(issuer, sub)` to a membership for `X-Workspace-ID`; project/task repository queries and document metadata lookups filter by that workspace. Missing and out-of-scope rows share not-found responses. Deletes use the same workspace filters; tasks are deletable by workspace members, while a project with tasks returns 409. Deleting an empty project detaches metadata but does not remove it. | Prior isolated PostgreSQL tests passed cross-workspace project/task/document reads, project/task updates, and same-shape not-found errors. New DELETE authorization cases and the in-memory contract passed/source added, but PostgreSQL cases were skipped in the latest run because `OPSDESK_TEST_DATABASE_URL` was unset. User-confirmed Auth0 membership denials provide separate manual evidence. | Project/task records are shared with all members of their workspace; the product has no per-user private ACL. Metadata isolation does not cover file bytes; upload/download and object-level checks belong to Phase 05. |
| Cross-workspace data leakage; tenant records | A user selects another workspace ID or queries an ID from another tenant. | Workspace header is only a selector hint; API checks verified subject membership and creates a per-request workspace-scoped repository. | Provider-independent anonymous-token tests and the passing isolated PostgreSQL authorization test include workspace selection and resource IDs. | No row-level security policy is configured in PostgreSQL; enforcement depends on these server-side scoped queries and tests. |
| Privilege escalation; membership roles | A member submits `role=owner`, a forged subject, or workspace identifier in an ordinary resource body. | Project/task schemas reject extra identity/scope fields. Role assignment exists only in an owner-only membership endpoint; an unassigned identity cannot provision itself. Initial owner bootstrap requires trusted database access and refuses a second bootstrap owner. | The isolated PostgreSQL suite passed member denial, unassigned-user denial, and forged workspace/role-field checks. | Membership removal, owner transfer, account disablement, and invitation acceptance/lifecycle are not implemented. Owners may assign the `owner` role to another subject. |
| Invalid, expired, or incorrectly validated tokens; all protected API data | Attacker supplies unsigned, altered, expired, wrong-issuer, or wrong-audience JWT. | Maintained PyJWT verifies RS256 signatures using issuer JWKS and enforces issuer, audience, `exp`, `iat`, and `sub`. Config absence fails closed for credential-bearing requests. | Automated tests generated RSA tokens and rejected invalid signature, expired, wrong issuer, wrong audience; anonymous protected-route test returns 401. User-confirmed manual API checks verified owner success and unprovisioned-user denial. | Tests use a fake JWKS resolver around real signature verification; live Auth0 JWKS key rotation/network behavior is not established by tests. Stateless tokens have no immediate revocation/denylist; short-lived access tokens limit the window. |
| Browser credential theft / CSRF; access token | Script injection attempts to read an access token or cross-site page submits an authenticated mutation. | Auth0 SPA SDK uses in-memory cache, no client secret, no persisted refresh token, and bearer headers rather than cookies. API CORS uses an explicit origin allowlist and does not enable credential cookies. | Frontend lint/type/build checks passed; source configuration reviewed. User-confirmed manual browser checks exercised real sign-in and sign-out. | XSS can still act as the current page; CSP and broader web security headers are future hardening. CORS is not an authorization mechanism. |
| Sensitive data in logs or errors; tokens and personal data | Request headers, tokens, DB details, or private tenant ownership are emitted to logs/errors. | Request logs omit headers and bodies; exception logs record error type/request ID, not raw DB exception. HTTP errors are sanitized; foreign-tenant resources return the same 404 shape as missing resources. `.env` files are ignored; checked-in examples contain placeholders; no Auth0 client secret is used in the frontend. | Reviewed middleware, error handlers, `.gitignore`, and environment examples; automated tests cover sanitized unexpected errors and out-of-scope 404s. `pip-audit --local` first found vulnerable local pip/setuptools/pytest tooling; the API venv was upgraded to pip 26.2.1, setuptools 84.0.0, and pytest 9.1.1. Rerun: no known vulnerabilities in installed dependencies; local `opsdesk-api` was skipped as unavailable on PyPI. | No API-level rate limiter is configured. Auth0 rate controls apply to interactive sign-in, not arbitrary API traffic; add edge/API throttling before public exposure. Deployment secret rotation, logs, tracing, and retention still require Phase 07 review. |

## Verification status

The latest API test run passed 24 tests and skipped 7 PostgreSQL-only tests because `OPSDESK_TEST_DATABASE_URL` was unset. The earlier Phase 04 PostgreSQL suite passed 30 tests with 0 skips before the new delete cases; the new PostgreSQL deletion behaviors still need a rerun. User-confirmed manual Auth0 checks verified sign-in/dashboard, sign-out, and owner/unprovisioned-user workspace access; expiry/revocation behavior remains unverified. The dependency audit initially identified vulnerable tooling and then reported no known vulnerabilities after upgrading the isolated API venv. Rate limiting and immediate JWT revocation remain explicit risks. This document records mitigations and evidence; it does not claim the threats are eliminated.
